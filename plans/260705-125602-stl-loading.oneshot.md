# One-Shot: STL Loading
Load STL files (binary + ASCII) in C++ backend, parse geometry, send vertex/face data to Electron/Vue frontend via IPC binary framing, display in Three.js viewport with orbit camera and build plate.

**Target dir:** /Users/ericolson/dev/forge/projects/guava-slicer
**Mode:** existing-codebase

## Stage 0: Context & Use Cases

**Project type:** application

### Context

Phase 2 of the guava-slicer roadmap. The IPC protocol is already proven (Phase 1). This feature adds the first real payload: loading STL files in the C++ backend, building indexed mesh geometry, transporting it to the Electron frontend via binary-framed IPC, and rendering it in a Three.js viewport with orbit controls, grid, and build plate visualization.

**Target file sizes**: 100MB+ STL files (2M+ triangles). The backend must handle parsing and vertex deduplication efficiently — no work in JS. Large file parsing must not block the IPC read loop.

**Non-goals**: No mesh editing, transforms (Phase 5), slicing (Phase 6), or non-STL formats.

### Use Cases

**UC-1: Load binary STL via file dialog**
Actor: User
Flow:
1. User clicks "Open" in the frontend
2. Electron shows native file dialog filtered to `.stl`
3. User selects a file
4. Frontend sends `load_mesh` command with file path
5. Backend parses binary STL on a worker thread, streams progress events
6. Backend deduplicates vertices, builds indexed mesh (position + normal + index buffers)
7. Backend sends geometry as binary IPC frames
8. Frontend wraps buffers into Three.js `BufferGeometry`, renders mesh
Success: Mesh visible in viewport with basic shading, orbit camera active
Failure: Backend returns error (file not found, invalid STL, read error) → frontend shows error message

**UC-2: Load ASCII STL**
Same flow as UC-1 but the parser detects ASCII format and switches to text parsing with fast_float for number extraction.

**UC-3: Viewport interaction**
Actor: User
Flow:
1. Mesh is displayed in viewport
2. Mouse controls: orbit (left-drag), zoom (scroll), pan (right-drag / middle-drag)
3. Blender-style numpad controls:
   - Numpad 1/3/7: Front / Right / Top orthographic views
   - Ctrl+Numpad 1/3/7: Back / Left / Bottom views
   - Numpad 5: Toggle perspective / orthographic
   - Numpad 2/4/6/8: Orbit in 15° increments
   - Numpad 0: Reset to default camera position
4. Grid and build plate remain visible as reference
Success: Smooth camera controls, numpad snaps to correct views, mesh stays centered on build plate

**UC-4: Large file handling**
Actor: User loading a 100MB+ STL
Flow:
1. File dialog → `load_mesh` command
2. Backend streams progress events (`{ "event": "progress", "data": { "triangles_read": N, "total": M } }`)
3. Frontend shows progress indicator
4. Parse completes, geometry sent as binary frames
Success: UI remains responsive throughout, progress updates visible
Failure: File too large for memory → backend returns structured error

## Stage 1: User-Facing Interfaces

**Decision: Option 2 — Viewport + info sidebar**

Three.js viewport fills the main content area. Top toolbar with "Open File" button and file name display. Progress bar overlay during large file loads. Right sidebar showing mesh stats: vertex count, triangle count, bounding box dimensions, file size. Blender-style numpad controls wired globally. Build plate grid rendered as GridHelper + plane.

Justification: The sidebar provides immediate feedback for validating the dedup/indexing pipeline and establishes the sidebar framework that later phases (slice params, support controls) will extend. Worth the marginal extra frontend work for a feature that's the foundation of the whole app.

## Stage 2: Behavior

**Actions:**
- Open file dialog: User clicks "Open File" → Electron shows native .stl file picker
- Load mesh: File selected → Backend parses STL on worker thread, deduplicates vertices, builds indexed geometry (position/normal/index buffers), sends via binary IPC frames, frontend renders in Three.js BufferGeometry
- Stream progress: During large file parse, backend emits progress events (triangles_read/total), frontend shows progress bar overlay
- Orbit camera: Left-drag or Numpad 2/4/6/8 → camera orbits around mesh center; numpad orbits in 15° steps
- Snap view: Numpad 1/3/7 (Ctrl for opposite) → camera snaps to front/right/top orthographic views
- Toggle projection: Numpad 5 → perspective/orthographic toggle
- Reset camera: Numpad 0 → default camera position
- Zoom: Scroll wheel → camera closer/further from mesh center
- Pan: Right-drag or middle-drag → camera pans on local XY plane

**Inputs:** File path (Electron dialog → IPC), mouse events (orbit/pan/zoom), keyboard (numpad views)
**Outputs:** 3D viewport rendering, mesh stats sidebar (vertex/triangle count, bounding box, file size), progress bar, error messages (toast/banner)

## Stage 3: Data Model

**Backend entities:**
- `Mesh`: vertices (flat `float[]` — x,y,z repeating), normals (flat `float[]`), indices (`uint32_t[]`), vertex_count, triangle_count, bounding_box {min: Vec3, max: Vec3}, source_path
- `Vec3`: x, y, z floats
- `BoundingBox`: min Vec3, max Vec3

**Frontend entities:**
- `MeshState`: THREE.BufferGeometry (wraps backend buffers directly), THREE.Mesh (scene object), stats {vertexCount, triangleCount, boundingBox, fileSize, fileName}, loading: bool, progress: {trianglesRead, total} | null, error: string | null

**IPC flow for `load_mesh`:**
1. Frontend → Backend: `{ "cmd": "load_mesh", "id": "<uuid>", "params": { "path": "/path/to/file.stl" } }`
2. Backend → Frontend (progress): `{ "id": "<uuid>", "event": "progress", "data": { "triangles_read": N, "total": M } }`
3. Backend → Frontend (binary): 3 length-prefixed binary frames — positions (float[]), normals (float[]), indices (uint32[])
4. Backend → Frontend (response): `{ "id": "<uuid>", "ok": true, "result": { "vertex_count": N, "triangle_count": M, "bounding_box": { "min": [x,y,z], "max": [x,y,z] }, "file_size_bytes": S } }`

**Invariants:**
- `vertices.size() == normals.size()` (both `3 * vertex_count` floats)
- `indices.size() == 3 * triangle_count`
- All indices `< vertex_count`
- Bounding box computed during parse, not re-derived
- Backend holds authoritative mesh state; frontend holds rendering copy

## Stage 4: Error Handling

**Decision: Option 2 — Production-grade with recovery**

Structured JSON errors at the IPC boundary with error codes (`IO_ERROR`, `PARSE_ERROR`, `INVALID_STL`, `OUT_OF_MEMORY`) and human-readable messages. Internal parser returns error codes for fast propagation. Adds: partial parse recovery (skip malformed triangles with warning count in response), memory-mapped file I/O for large files to avoid OOM, and detailed error context at the boundary (e.g., byte offset where parse failed). Frontend shows errors as dismissible banners with the error message.

Justification: Real-world STL files from cheap slicers are frequently slightly malformed. Skipping bad triangles with a warning count is better than failing the entire load. Memory-mapped I/O is essential for 100MB+ files — reading the whole file into a buffer doubles memory usage. Worth the complexity since this is the foundation I/O path for the entire app.

## Stage 6: Persistence

**Decision: Option 1 — In-memory only**

Parsed mesh lives in backend memory as flat arrays. Frontend holds a rendering copy in GPU buffers. No disk persistence — user re-opens the STL file next session. Phase 3 (Project Persistence) will add save/load with its own design.

Justification: Zero complexity, avoids cache invalidation issues, and doesn't overlap with the upcoming Phase 3 project persistence work. The fast parser + mmap makes re-parsing acceptable even for large files.

## Stage 7: Tech Stack

**Decision: Option 2 — microstl + linalg.h, with result-type wrapper**

- STL parser: microstl (MIT, single header, callback-based) vendored unmodified. A wrapper layer translates exceptions into `util::Result<T, E>` return types — microstl source stays untouched in `vendor/`, the wrapper catches at the boundary and converts to error returns.
- Linear algebra: linalg.h (public domain, single header, ~1200 LOC) vendored. Provides `linalg::vec<float,3>` and `linalg::mat<float,4,4>` — carries forward to Phase 5 transforms and Phase 6 slicing without replacement.
- Number parsing: fast_float vendored for ASCII STL path (used inside the wrapper's ASCII callback).
- Mesh data structure: Indexed triangle soup — flat `std::vector<float>` for positions/normals, `std::vector<uint32_t>` for indices. Vertex dedup via hash map during parse.
- Memory-mapped file I/O via platform abstraction for 100MB+ files.

Justification: microstl handles the STL format edge cases (binary/ASCII detection, malformed files) so we don't own that complexity. Vendoring it unmodified and wrapping at the boundary keeps the vendor rule intact while providing no-throw ergonomics for the rest of the backend. linalg.h avoids a throwaway vec3 that gets replaced next phase.
