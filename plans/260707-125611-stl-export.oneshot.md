# One-Shot: STL Export
Export model mesh and support/raft meshes as STL files for inspection in external slicers (Bambu Studio).

**Target dir:** /Users/ericolson/dev/forge/projects/guava-slicer
**Mode:** existing-codebase

## Stage 0: Context & Use Cases

**Who it's for:** The guava-slicer user preparing a model for FDM printing. After placing supports and generating a raft, they need to get the result into Bambu Studio for final slicing and G-code generation.

**What it solves:** Currently the only STL export path is the headless CLI (`support-test`). There's no way to export from the GUI. This phase adds a single combined export (model + supports + raft as one mesh) with a native save-as dialog.

**Constraints:**
- Export bakes in all applied transforms (rotation, translation, scale) — the STL is print-ready
- Single export mode: combined (model + supports + raft merged into one STL)
- Full native save-as dialog via Electron's `dialog.showSaveDialog`
- Binary STL format (not ASCII — smaller files, faster writes)
- Export is not undoable (it's a read-only operation on current state)

**Non-goals:**
- Model-only or supports-only export (future work)
- Format conversion (OBJ, 3MF, etc.)
- Direct printer integration
- Export history or recent exports list

**Project type:** application

**Use Cases:**

**UC1: Export combined STL**
- Actor: User
- Trigger: Click "Export STL" button in sidebar or press Ctrl+E
- Flow:
  1. User has a loaded model with supports/raft generated
  2. User clicks "Export STL" or presses Ctrl+E
  3. Native save-as dialog opens, defaulting to `<original-filename>_combined.stl`
  4. User picks location and filename
  5. Backend bakes transforms into model vertices, merges model + support + raft geometry, writes binary STL
  6. Progress indicator shown during write (for large meshes)
  7. Success toast/notification with file path
- Success: STL file written, opens correctly in Bambu Studio
- Failure: Write error → error toast with message (disk full, permission denied, etc.)

**UC2: Export with no supports**
- Actor: User
- Trigger: Same as UC1, but no supports have been generated
- Flow: Same as UC1, but exported STL contains only the model mesh (with baked transforms). No warning needed — exporting a bare model is valid.

**UC3: Cancel export**
- Actor: User
- Trigger: User dismisses the save-as dialog
- Flow: No file written, no state change. Silent — no toast.

## Stage 1: User-Facing Interfaces

**Decision: Sidebar export button + Ctrl+E hotkey**

"Export STL" button in the left sidebar (below the existing support generation controls). Ctrl+E keyboard shortcut. Both trigger Electron's native `dialog.showSaveDialog` with a default filename of `<original-filename>_combined.stl`. No custom export panel — the save-as dialog is the entire UI surface. Success/failure communicated via toast notification.

Justification: Matches the existing sidebar-driven workflow. Native save-as dialog is zero custom UI work and behaves consistently across macOS/Windows. When model-only/supports-only modes are added later, the button can evolve into a dropdown or panel without breaking the current flow.

## Stage 2: Behavior

**Actions:**

| Action | Trigger | Inputs | Effect |
|--------|---------|--------|--------|
| Export combined STL | "Export STL" button click or Ctrl+E | None (uses current state) | Opens save-as dialog, writes binary STL |
| Write STL file | User confirms save-as dialog | File path from dialog | Backend bakes transforms into model vertices, merges model + support meshes, writes binary STL to disk |
| Cancel export | User dismisses dialog | None | No-op |

**Inputs:**
- Keyboard: Ctrl+E (export hotkey)
- Mouse: Click "Export STL" button in left sidebar
- Dialog: File path from native save-as dialog

**Outputs:**
- File: Binary STL at user-chosen path
- UI: Success toast with file path, or error toast on failure
- IPC: `export_stl` command → backend → `{ok: true, result: {path, triangle_count, file_size_bytes}}` or `{ok: false, error: {...}}`

**Behavior details:**
- Transform baking: apply `TransformState::composite_matrix()` to every model vertex before writing. Support/raft vertices are already in world space (generated after transforms), so they're written as-is.
- Default filename: strip extension from `mesh.source_path`, append `_combined.stl`
- If no mesh is loaded, the Export button is disabled (grayed out)
- Export is not a command (no undo/redo) — it's a pure read of current state

## Stage 3: Data Model

No new entities. Export reads existing structures:

- **`mesh::Mesh`** — `vertices` (flat float array, 3 per vertex), `indices` (uint32, 3 per triangle), `triangle_count`, `source_path`
- **`transform::TransformState`** — `composite_matrix()` returns `Mat4` (4x4 column-major)
- **`support::SupportCollection`** — `mesh_vertices` (flat float array), `mesh_indices` (uint32 array)
- **`stl_writer::write_combined_stl()`** — already handles merging two meshes into one binary STL

**Transform baking invariant:** Model vertices are stored in original (pre-transform) space. The composite matrix must be applied to each vertex `(x, y, z)` before export. The result replaces the vertex positions in the export buffer only — `AppState.mesh` is not mutated.

**Index offset invariant:** When merging model + support meshes, support indices must be offset by the model's vertex count (already handled by `write_combined_stl`).

## Stage 4: Error Handling

**Decision: Structured error at IPC boundary, simple toast on frontend**

`export_stl` returns `{ok: false, error: {code: "IO_ERROR", message: "..."}}` on write failure or `{ok: false, error: {code: "NO_MESH", message: "..."}}` if no mesh is loaded. The frontend shows an error toast with the message. No partial-write cleanup, no retry — user fixes the issue and tries again.

Justification: Consistent with the existing error handling pattern across all IPC commands. Export is a low-risk operation (worst case is an orphan partial file) and adding atomic-write complexity is not justified for the initial implementation.

## Stage 5: Replayability

## Stage 6: Persistence

## Stage 7: Tech Stack

**Decision: New `export_combined_stl()` in `stl_writer` that takes a transform matrix**

Add a new function to `stl_writer` that accepts model vertices + indices, a 4x4 transform matrix, support vertices + indices, and an output path. It bakes the transform into a temporary copy of model vertices, then writes the merged binary STL. Support vertices are written as-is (already in world space). If no supports exist, it writes model-only.
